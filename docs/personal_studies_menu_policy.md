# 管理者別の書房と権限別メニュー

## 個人書房

`/study` はログインした管理者本人のJupyterへ接続する。管理者、操作担当者、閲覧者の既存の操作権限は変更せず、書房のHTTP・WebSocket・起動APIは管理者認証を必須とする。APIキーだけでは書房の本人を特定できないため、ブラウザーのログインセッションを使う。

保存先は利用者設定のNotebookルート配下の `users/<ユーザーIDのSHA-256>/`。ユーザー名の変更では移動しない。Jupyterの導入済み版は共有するが、プロセス、トークン、実行時フォルダー、起動・停止状態は管理者別に持つ。不要な管理者のJupyterを先行起動せず、本人が書房を開いた時に起動する。

通常Chat・Plan/Actの書斎保存は依頼した管理者の書房へ送る。群の成果は最初に管理者が成果作成・自律設定・投稿・Forge計画・再保存を操作した時に書房の所有者を記録し、その群の自律処理でも同じ保存先を使う。後から別の管理者が群へ参加しても保存先を無断変更しない。群の成果本文の共有範囲と個人書房のファイル閲覧は別であり、他の管理者が所有する保存リンクは自分の書房には存在しない場合がある。未割当の自律群では保存先未準備を明示し、管理者の操作後に保存を再試行できる。

所有者は `.wentian/study-group-owners.json` へ原子的に保存する。会話本文や認証情報は含めない。

旧共有Notebookルートは削除・自動移動しない。書房の「旧共有書房のデータ」から、管理者が自分の書房へコピーできる。同名ファイルは上書きせず、原本を保持する。`users` 以下の個人領域、リンク・ハードリンク経由は取り込まない。

この分離はアプリの接続先・データ保存先の分離であり、同じOSユーザーで実行するJupyterカーネルに対するOSレベルのサンドボックスではない。管理者の任意コード実行を相互に隔離する用途では、別OSアカウントやコンテナー等が必要となる。

## 左メニューの設定

管理・設定の「メニュー表示設定」(`/menu-settings`) で管理者・操作担当者・閲覧者ごとのチェック表を保存する。設定は `.wentian/menu-policy.json` へ原子的に永続化する。

管理者は既定で全項目、操作担当者は共通の会話系項目と既存の作業項目、閲覧者はホーム・個別チャット・本人設定・孵化器・AIグループを既定とする。表示は機能の操作許可を与えない。APIの認証・権限検査は従来どおりであり、表示対象に設定しても管理者限定操作は管理者以外に許可されない。

管理者の「ユーザー管理」「メニュー表示設定」は、管理経路を失わないため非表示にできない。空になった分類は隠し、言語変更でも項目IDは変えない。設定を保存した画面は直ちに、他の画面はフォーカス復帰・30秒の再取得で更新する。メニュー検索も非表示状態を尊重する。

API:

- `GET /api/navigation/menu`: 本人の権限の表示項目。
- `GET /api/navigation/policy`: 管理者用の3権限の設定。
- `PUT /api/navigation/policy`: 管理者・同一サイト限定の変更。
- `POST /api/study/import-legacy`: 管理者本人の旧共有データ取り込み。

## 検証

一時ディレクトリー、模擬Jupyter、架空の利用者で試験し、本番ユーザー・共有Notebook・外部サービスは試験から変更しない。管理者別の起動停止、HTTPとWebSocketの転送先、所有者の永続化、旧データ取り込みの除外・上書き防止、3権限のメニュー設定と認可、三言語表示、既存の成果保存とナビゲーションを確認する。

検証結果：書房・ナビゲーションの25試験、Chat・群・個人書房等の50試験、メニュー設定画面を含む3試験の各実行で失敗0。対象の重複を含む。型検査成功。既存の待受設定を保持して再起動し、`/health`、`/study`、`/menu-settings` の200、未ログインの書房状態API・メニュー設定APIの401を確認した。実際の複数管理者でJupyterを同時起動する検証は未実施であり、中継先の分離は隔離したHTTP/WebSocketサーバーで確認した。
