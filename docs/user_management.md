# ユーザー管理とアカウント復旧

2026-10-19

## 管理者の操作

ホームの「管理・設定」→「ユーザー・アカウント」（`/#users`）から「ユーザー管理」を開く。

- 新規作成：ユーザー名・表示名・権限・有効状態・初期パスワードを指定する。
- 編集：ユーザー名、表示名、権限、有効状態を変更する。ログイン名を変更してもユーザーIDは保持し、DMと群の関連付けを維持する。
- パスワードのリセット：編集画面で新しいパスワードと確認欄を入力する。空欄なら既存パスワードを維持する。
- 有効／無効：無効化するとログインと既存セッションを停止する。再有効化で同じIDを利用できる。
- 接続をすべて終了：対象利用者の全ログインセッションを失効させる。
- 削除：アカウントを削除する。確定済みの群履歴やDMのファイルは削除しない。再作成は別IDとなるため、一時停止には無効化を使う。
- 検索・絞り込み：ログイン名／表示名、権限、有効状態から一覧を絞る。
- 操作履歴：実行日時・操作種別・対象ID・実行者IDを確認する。

権限は管理者（admin）、操作担当者（operator）、閲覧者（viewer）。管理画面・管理APIは管理者だけが操作できる。その他の操作可能範囲は各機能の既存権限に従う。

ユーザー名は3～40文字の英数字・ピリオド・ハイフン・アンダースコアで、小文字として保存する。重複は拒否する。表示名は40文字以内、パスワードは12～1024文字。

最後の有効な管理者の削除・無効化・降格、およびログイン中の本人の削除を拒否する。同時操作でも最後の管理者を失わない。名前・権限・有効状態・パスワードの変更は対象利用者の全セッションを失効させる。表示名だけの管理者による変更ではセッションを維持する。

## 本人の操作

左メニューの「ユーザー・アカウント」（`/#users`）を開く。管理者は「自分のアカウント」へ切り替え、その他の利用者は本人設定だけを表示する。旧`/account`は統合先へ転送する。現在のパスワードを確認して、本人のユーザー名・表示名・パスワードを変更する。権限と有効状態は変更できない。保存後は全セッションを失効させ、再ログインを求める。自分の全セッションを終了するボタンも用意する。

## ログインできない管理者の復旧

他の管理者がログインできる場合は、管理画面から対象のパスワードをリセットする。他にログインできる管理者がいない場合は、サーバーのファイル操作権限を持つ人がローカルで次を行う。

1. Wentian Daemonを停止する。
2. 利用者台帳を指定して、既存管理者のIDを確認する。
3. IDを指定して復旧し、新しいパスワードを非表示で二度入力する。
4. サーバーを元のホスト・ポート設定で再起動し、ログインする。

台帳は利用者設定 `WENTIAN_USER_STORE` の保存先。未指定の場合はサーバー起動作業場所の `.wentian/control-center-users.json`。下記の保存先は実際の台帳の絶対パスへ置き換える。

```powershell
# PowerShell版：一覧は読み取りのみ。
.\scripts\recover-user.ps1 -Store '<台帳の絶対パス>' -List
.\scripts\recover-user.ps1 -Store '<台帳の絶対パス>' -UserId '<既存管理者ID>'
# ログイン名も変更する場合のみ -Username 'new-admin' を付ける。
```

```powershell
# Python版：Windows Python Launcherを利用する例。
py -3 scripts/recover-user.py --store '<台帳の絶対パス>' --list
py -3 scripts/recover-user.py --store '<台帳の絶対パス>' --user-id '<既存管理者ID>'
# ログイン名も変更する場合のみ --username new-admin を付ける。
```

復旧は既存の管理者だけを対象にし、IDと権限を維持して再有効化する。一般利用者を管理者へ昇格させない。Daemon台帳で稼働中と判定した場合は変更を拒否する。Daemon管理外で直接起動したサーバーも、実行者が事前に停止すること。カスタム環境では同じインストール元・台帳を指定し、復旧は一人が実行する。

パスワードを引数・環境変数・出力へ渡さず、標準入力でローカルのNode.js処理へ渡す。台帳全体を削除・再作成する方式ではない。環境変数 `WENTIAN_ADMIN_USERNAME` / `WENTIAN_ADMIN_PASSWORD` は初期作成用で、登録済みアカウントのリセットには使わない。メール送信による本人確認・パスワード再発行は追加していない。

## API・保存

| API | 対象 |
|---|---|
| GET /api/control-center/users | 管理者：一覧・セッション数 |
| POST /api/control-center/users | 管理者：作成 |
| PATCH /api/control-center/users/:id | 管理者：編集・パスワードリセット |
| DELETE /api/control-center/users/:id | 管理者：削除 |
| POST /api/control-center/users/:id/revoke-sessions | 管理者：全接続終了 |
| GET /api/control-center/users/audit | 管理者：操作履歴 |
| GET/PATCH /api/control-center/profile | ログイン本人：取得・再認証して変更 |
| POST /api/control-center/profile/revoke-sessions | ログイン本人：全接続終了 |

更新は直列化し、台帳の原子的保存が成功してからメモリを更新する。入力不正・重複・保存失敗で途中の変更を残さない。パスワードはscryptで保存し、公開ユーザー情報や操作履歴へハッシュ・パスワード・セッショントークンを含めない。操作履歴は直近1000件を台帳に保存する。セッションはメモリ上だけに保持し、再起動で失効する。変更APIは別オリジンからの操作を拒否する。

## 検証

試験は一時台帳・架空利用者・模擬応答へ隔離し、実際の利用者やパスワードを変更しない。作成・重複拒否・名前変更・パスワードリセット・本人再認証・権限昇格拒否・最後の管理者の競合保護・セッション失効・履歴・復旧・画面一連操作・中日英表示を検証する。既存のホーム・メニュー・DM・公開参加とサーバー構成も回帰試験の対象にする。

検証結果：型検査成功。関連42試験成功、復旧CLI・メニュー更新等の追加実行18試験も成功（重複を含む）。Python版・PowerShell版の構文検査成功。実行時の待受設定を維持してサーバーへ反映した。
